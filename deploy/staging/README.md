# Staging runtime

`compose.yaml` is what runs on the staging host. It is not a development stack
(that is `compose.yaml` at the repository root). See
`docs/security/THREAT-MODEL-DEPLOY-PIPELINE.md` for the design.

- **Images** `paxoficloud-php:<git sha>` and `paxoficloud-nginx:<git sha>` are
  built in CI from `docker/production/` after `composer install --no-dev`. They
  are never built on the host or pushed to a registry.
- **Secrets** are read from env files in `/etc/paxoficloud` on the host. The
  deploy agent generates them on the first release (32 bytes from
  `/dev/urandom` each, files mode 0600) and never prints them; they never pass
  through CI or the logs:
  - `app.env`: `DB_USERNAME`, `DB_PASSWORD`, `REDIS_PASSWORD` (the web tier;
    never the provider-credential KEK)
  - `mysql.env`: `MYSQL_RANDOM_ROOT_PASSWORD=yes`, `MYSQL_DATABASE`,
    `MYSQL_USER`, `MYSQL_PASSWORD`
  - `redis.env`: `REDIS_PASSWORD`
  - `outbox-public.env`: `EMAIL_OUTBOX_PUBLIC_KEY` (web tier: seals queued
    email; the key pair is generated with libsodium in the release image)
  - `outbox-secret.env`: `EMAIL_OUTBOX_SECRET_KEY` (mail worker only)
  - `mail-providers.env`: `POSTMARK_SERVER_TOKEN`, `RESEND_API_KEY`,
    `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD_B64`,
    `EMAIL_PROVIDER`, `EMAIL_RECIPIENT_ALLOWLIST`, piped by the deploy
    workflow from the `staging` environment to the `mail-secrets` verb over
    the tunnel (stdin, never argv or logs).
  - `web.env`: `TURNSTILE_SITE_KEY` (variable) and `TURNSTILE_SECRET_KEY`
    (secret), piped the same way to the `web-secrets` verb and mounted into
    the `php` container only (identity threat model §6.12). These two files
    are the only secrets that come from CI.
  - `identity-keys.env`: `MFA_SECRET_KEYS`, `MFA_SECRET_ACTIVE_KEY` (TOTP
    secret encryption) and `MFA_RECOVERY_KEY` (recovery-code hashing),
    generated by the agent on first release, mounted into `php` only
    (identity threat model §6.13). Losing this file locks every customer who
    turned on two-step verification out of it, so back it up with the host.
- **Mail worker:** `mail-worker` (compose profile `mail`) runs
  `bin/paxoficloud mail:work`. It is the only container with the outbox
  secret key and provider tokens, and the only one on the `egress` network.
  The agent enables it only when `mail-providers.env` holds a provider token
  or a complete SMTP relay (host plus password).
  On staging, `EMAIL_RECIPIENT_ALLOWLIST` is the same value as
  `STAGING_ALLOWED_EMAILS`, so mail can only reach people allowed through
  Cloudflare Access (threat model E-9).
- **Web app:** the Nginx image also carries the customer-portal build from
  `frontend/` (built in a pinned Node stage; nothing else from that stage
  ships). Nginx serves it at `/` with its own CSP and security headers, and
  routes only `/health/*` and `/api/*` to PHP.
- **Staff console:** the same image carries `admin.html`, served only on the
  admin host (`cloud-staging-admin.paxofi.com`, `ADMIN_URL` in
  `compose.yaml`), which routes only `/health/*` and `/admin-api/*` to PHP and
  has a stricter CSP. The customer host refuses `/admin-api` and `admin.html`
  (identity threat model §6.19). Both hosts sit behind the same Cloudflare
  Access email gate; staff then sign in with password, authenticator code and
  emailed code, or with an optional passkey (§6.20).
- **Exposure:** only Nginx is published, on `127.0.0.1:8080`. `cloudflared` on
  the host forwards to it. MySQL and Redis sit on an internal network.

## Smoke test

Builds nothing. It runs the stack from locally built images with throwaway
secrets, then checks that it serves and is hardened:

```sh
APP_VERSION=<tag> deploy/staging/smoke-test.sh
```

CI runs the same script in the "Production images smoke test" job.

## Deploy agent (`host/paxoficloud-deploy`)

Installed by cloud-init as `/usr/local/sbin/paxoficloud-deploy` and bound to the
`deploy` user's key as a forced command. Because cloud-init installs it, a
change to this script (or to `compose.yaml`) reaches the host only when the
infrastructure workflow replaces the instance (plan, then apply); a deploy alone
keeps the old copy. It accepts exactly these verbs:

| Verb | Does |
|---|---|
| `load` | Reads a gzip `docker save` stream from stdin. Keeps only `paxoficloud-php:<sha>` / `paxoficloud-nginx:<sha>`; anything else is removed and the command fails. |
| `release <40-hex sha>` | Generates secrets on first run (separate MySQL owner and runtime users, §6.22), starts MySQL/Redis, runs `bin/paxoficloud migrate` and `db:grants paxoficloud_app` as the schema owner, starts the new version and waits for `/health/ready`. On success records `current`/`previous` and prunes older images; on failure restarts the previous version and exits 1. |
| `mail-secrets` | Reads `NAME=value` lines from stdin (max 8 KiB). Accepts only `POSTMARK_SERVER_TOKEN`, `RESEND_API_KEY`, `SMTP_HOST`, `SMTP_PORT` (465/587), `SMTP_USERNAME`, `SMTP_PASSWORD` (stored base64-encoded as `SMTP_PASSWORD_B64`), `SMTP_TLS_NAME` (optional; must be `SMTP_HOST` or a parent domain of it), `EMAIL_PROVIDER` and `EMAIL_RECIPIENT_ALLOWLIST`, each format-checked; any bad line rejects the whole update. Writes `mail-providers.env` atomically (0600) and logs names only. |
| `web-secrets` | Reads `NAME=value` lines from stdin (max 4 KiB). Accepts only `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` (8–128 of `A-Z a-z 0-9 _ -`, or empty to turn the challenge off); any bad line rejects the whole update. Writes `web.env` atomically (0600) and logs names only. Hosts installed before this verb existed answer exit 64; the workflow then warns and deploys with the challenge off until an infra apply replaces the host. |
| `staff-bootstrap` | Reads `EMAIL=` and `NAME=` from stdin (max 1 KiB; fixed formats, no shell metacharacters) and runs `bin/paxoficloud staff:bootstrap` in the running release with them as arguments (no shell). Logs neither value. Once a staff manager exists, the same command adds the founder roles to the sole active Security Admin with that email (§6.23). Exit 2 when the app refuses (another staff member is active, the address is not the founder's, or it is already staff). Used by the workflow action `staff-bootstrap`. |
| `status` | Prints the current and previous release SHAs, the containers, and a mail summary: worker enabled or disabled, `EMAIL_PROVIDER`, the number of allow-list entries, the names (never values) of the mail settings that are set, and `mail:status` (outbox counts plus the latest delivery problems with their fixed failure reason, e.g. `suppressed-not-allowlisted`). The deploy workflow runs it after every deploy; run the workflow with `action: status` to print it without deploying. |

Every run is appended to `/var/log/paxoficloud/deploy.log` (time, verb, SHA,
result). Migrations are forward-only (MIGRATIONS.md), so rolling back code never
needs a schema rollback.

`host/test-deploy-agent.sh` exercises the agent against the real images (bad
input, a release, a broken release that rolls back, pruning). CI runs it after
the smoke test.

## First staff Security Admin

1. In the `staging` environment add the secret `STAGING_FIRST_ADMIN_EMAIL`
   (also listed in `STAGING_ALLOWED_EMAILS`, so Access lets you in and the mail
   worker may send to it) and the variable `STAGING_FIRST_ADMIN_NAME`.
2. Run **PaxofiCloud Staging Deploy** with `action: staff-bootstrap`.
3. Open the "staff invitation" email and follow the link within 24 hours:
   `https://cloud-staging-admin.paxofi.com/enrol`. Choose a password (15+
   characters), scan the QR code with an authenticator app (Google
   Authenticator, Microsoft Authenticator, …), enter its code, and save the 10
   recovery codes. The account is active at once.
4. Sign in at `https://cloud-staging-admin.paxofi.com/`: email and password,
   then the authenticator code, then the 6-digit code emailed to you. From
   "Your sign-in" you can add an optional passkey. Invite further staff from
   the console. The bootstrap action no longer invites anyone from now on.

### Founder roles (identity threat model §6.23)

While you are the **only** active staff member, nobody else can grant you a
role. Run the same `action: staff-bootstrap` again (same secret and variable):
it adds the founder roles (today: Catalogue, for products, prices and provider
costs) to your account. It never grants Super Admin. Every grant is audited and
you get a "Roles were added to your staff account" email; that email is the
confirmation (hosts set up before this change log "invitation queued" even
when roles were granted). It refuses (exit 2) as soon as a second staff member
is active; from then on roles are granted in the console by another manager.
